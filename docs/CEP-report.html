COMPLEX ENGINEERING PROBLEM

SecPatch-DAG

Selecting and scheduling software patches across limited maintenance windows

NED University of Engineering and Technology
Department of Computer Science and Information Systems
CT-363 · Design and Analysis of Algorithms

Abstract

A maintenance team must choose which updates will fit into the available downtime and determine a safe execution order. A high-benefit patch can consume an entire window, while an urgent application update may have to wait for a library update. This project separates allocation from sequencing and connects them through a common set of patch actions. It combines capacity-vector dynamic programming, divide-and-conquer over independent dependency groups and a greedy ready-set scheduler. A faster approximate selector provides a single-window comparison.

On a synthetic instance with 12 packages, 20 dependency edges and windows of 18 and 13 minutes, the reconstructed plan earns 82 benefit units. Retiring the two highest-priority packages reduces the optimum to 78. Introducing three dependency edges reduces it to 71. Updating the affected group yields the same assignment as rebuilding all three groups.

ENGINEERING CONTEXT

Introduction and literature review

Imagine a maintenance engineer with two shutdown periods tonight. A 25-minute job cannot be split into an 18-minute shutdown and a 13-minute shutdown. Two separate jobs might fit, and the team still has to decide which to perform first. The application returns a selected set, an assignment to windows and a minute-by-minute order the engineer can inspect.

Literature review

NIST treats enterprise patching as preventive maintenance and emphasizes planning across operational and security stakeholders [1]. This motivates a bounded downtime model. The benefit units and priorities here are synthetic estimates. They represent planning inputs rather than measured loss avoided.

Tarjan’s depth-first search identifies strongly connected components [2]. A cycle means the affected packages cannot satisfy a strict “before” relation. The planner conservatively blocks those packages and packages depending on them. This is a policy choice: a real team might instead test and deploy an atomic batch.

The multiple-knapsack model assigns an item to at most one bin while respecting each bin’s capacity [3]. We adapt it to chronological maintenance windows and add dependency constraints. Smith’s ordering rule addresses a separate decision: for independent jobs on one machine, ordering by weight divided by processing time minimizes total weighted completion time [4]. Dependencies limit the eligible jobs, so that optimality proof only covers the independent case.

WP1 / WP2

Problem formulation and assumptions

Each approved patch i has a positive integer duration dᵢ, a fixed nonnegative benefit bᵢ, an urgency weight pᵢ, an asset and a package. Window j has integer capacity Cⱼ. For binary xᵢⱼ, maximize Σᵢⱼ bᵢxᵢⱼ subject to Σⱼxᵢⱼ ≤ 1 and Σᵢdᵢxᵢⱼ ≤ Cⱼ. A mandatory patch must be assigned exactly once. Partial coverage is permitted for optional patches. Windows are chronological and use one maintenance crew; actions are indivisible.

A hard action prerequisite forces inclusion and earlier execution. A package edge means that, when both patches are selected on the same asset, the prerequisite executes first. An edge alone does not require installing another patch. Transitive package order is respected even if an intermediate package has no selected action. Legacy datasets without asset identifiers share an unnamed scope. Separately, a package dependency cycle blocks its members and downstream dependents.

Priority is an ordering weight, not a second copy of benefit. Within a window the scheduling objective is to reduce ΣᵢpᵢFᵢ, where Fᵢ is completion time from that window’s start. The primary allocation objective is total benefit. Among equal-benefit root states we prefer fewer minutes, then the smaller usage vector in lexicographic order. The solver does not jointly optimize urgency across all equivalent allocations.

PART A / MODEL AND PROOF

Exact allocation across windows

Build an undirected group graph with the package edges and the package endpoints of all hard action requirements. Distinct connected components share only the window capacities. A dependency between two groups would have joined them, so groups can be evaluated independently before their capacity demands are reconciled.

Group table G[u] = maximum feasible benefit using exactly u minutes
                    (u is one entry per window).
For each group:
  Analyze package cycles and reachability.
  For each assignment of its jobs to skip or one permissible window:
    Reject blocked, missing mandatory, over-capacity or precedence failures.
    Keep the highest benefit and its assignment at usage vector u.
Merge(groups):
  If one group remains, return its table.
  Split groups in half; recursively obtain tables L and R.
  For each pair of states a and b with a+b within capacity:
    T[a+b] = max(T[a+b], L[a] + R[b]); retain winning child pointers.
  Return T.
Choose the best feasible root state. Follow pointers to recover jobs.

Base case and optimal substructure

The empty feasible allocation has value zero at the all-zero vector. An impossible state is absent. A mandatory job can make the entire table empty. At a leaf, feasible assignments are enumerated exactly once because each action receives exactly one choice. At an internal node every feasible assignment splits uniquely into left and right assignments with usages a and b. Replacing one half with a better feasible plan at the same usage preserves all constraints and improves the total. Thus an optimum uses optimal child entries at some split. Conversely, each compatible pair is feasible, proving the recurrence by induction.

Why running one knapsack per window fails

Consider capacities 2 and 3 and three actions of (minutes, benefit) equal to (2,6), (3,8) and (3,7). Only one three-minute action fits the larger window. The optimum is 14. Pooled capacity loses this individual limit, and solving each window with a fresh list can award the same action twice. Capacity vectors and disjoint action groups enforce both requirements directly.

PART B / CORRECTNESS

Scheduling and comparison methods

Schedule(selected jobs for a window):
  While jobs remain:
    Ready = jobs whose selected prerequisites have finished.
    If Ready is empty, report a conflict.
    Select maximum priority / duration; break ties by action ID.
    Append its interval, advance elapsed time, remove the job.

Only ready jobs can be appended. By induction each prefix respects precedence. In the independent-job case, consider adjacent jobs i and j. Scheduling i then j incurs weighted completion cost pᵢdᵢ + pⱼ(dᵢ+dⱼ), apart from common terms. Swapping them changes the comparison to pᵢdⱼ versus pⱼdᵢ. Thus i should precede j when pᵢ/dᵢ ≥ pⱼ/dⱼ. Repeated exchanges produce ratio order. With constraints, a ready job may unlock a valuable successor; this exchange argument no longer proves global optimality.

Single-window comparison

Greedy: force mandatory closure, or report infeasible. Scan by
  benefit/minute, priority, then ID. Keep feasible closures. Compare
  the result with the best feasible single closure plus forced jobs.
Plain DP: best[i,c] = max(skip i, bᵢ + best[i-1,c-dᵢ]) if i fits.
  Start with zeros; iterate capacity downward; backtrack take flags.
Tree DP: condition on taking a parent. Merge feasible child tables
  over all splits of remaining capacity. Backtrack recorded prefixes.
CP-SAT: one binary variable per job; impose capacity, prerequisite,
  mandatory and blocked constraints. Maximize benefit; read status.

For ordinary optional independent items, discard individually oversized items for the proof. Fractional knapsack bounds the optimum by the value of the density prefix plus at most the next item. Greedy’s final value covers that prefix; the best feasible singleton covers the next item. Their maximum is at least half the optimum. If all items fit, greedy is exact. Mandatory actions and hard prerequisites invalidate this guarantee. The dashboard now shows the bound only on eligible valid runs.

Plain DP is exact because every optimum either includes the last item once or excludes it. Tree DP is exact because subtrees are independent conditional on taking the parent and splitting capacity. Single-window DP declines unsupported general hard-prerequisite graphs and oversized tables. CP-SAT is an optional benchmark with a time limit; only a proven optimum receives the exact label.

WP3 / IMPLEMENTATION COST

Complexity and incremental repair

Let V and E count packages and edges, n count actions, h count action prerequisite links, k count windows, and U = ∏ⱼ(Cⱼ+1). For a fixed total capacity C, U ≤ (1+C/k)ᵏ. The individual capacities determine the actual state count. Bounds below include the implementation’s extra passes when they affect the result.

ProcedureTime and storage reasoning
Graph screeningTarjan’s DFS visits each node and edge once, O(V+E). The implementation also sorts adjacency, maintains a sorted topological ready list and traverses reachability in both directions per node. A conservative overall bound is O(V(V+E)+V² log V+E log(E+1)) time and O(V²+E) storage for the materialized graph analysis.
Single-window comparisonsGreedy sorts then copies candidate sets, walks prerequisite closures and sums durations: O(n(n+h)+n log n) time, O(n+h) auxiliary space including traces. Plain DP table: O(nW) time and O(nW) storage with reconstruction. Tree DP: O(nW²) time and O(nW) storage. Before either DP the blocked-job propagation can add O(n(n+h)) time. CP-SAT builds O(n+h) terms and may search exponentially many binary choices.
Ready-set schedulerFor s selected jobs with r order links, up to s rounds rescan remaining jobs and links and sort ready jobs. O(s(s+r)+s² log(s+1)) time, O(s+r) including input links and output. Conditional order links may be quadratic in job count.
Multiple-window leavesA group of g jobs has at most (k+1)ᵍ placements. Each candidate checks capacities and order and may run the scheduler for every window. One conservative per-placement bound is O(k(g+1)³ + g²V), allowing dense prerequisite sets and package closure. A leaf stores at most U entries, each holding up to g assignments. Global brute force has (k+1)ⁿ placements before checks.
Balanced DP mergesCombining child tables of sizes L and R costs O(kLR) time. With t groups, at most O(tkU²) merge time, O(tU(k+n)) conservative storage including leaf assignments and retained child pointers. Divide depth is O(log t). Sparse reachable states usually reduce work.

Incremental update. Rebuild group membership, compare each group’s nodes, edges, actions and capacities to cached inputs; reuse exact matches, rebuild changed groups and remerge capacity tables. Splits and joins change keys. A global merge is still needed because groups compete for the same minutes. Group discovery and key building still scan inputs (including per-group scans). The saving is avoiding graph analysis and placement enumeration for unchanged groups. A change touching all groups can cost as much as a fresh plan.

Sensitivity. Each package has one action, so retiring the two packages with the highest action priorities removes gateway (10) and identity (9) and their incident edges. The replacement plan fills both windows again. It earns four fewer units, and its greedy sequence changes because policy and common now precede their selected dependents. A change in urgency alone would not remove work; retirement is the explicit experiment here.

VALIDATION AND CONCLUSIONS

Failure cases and evidence

Three-edge disruption. Starting again from baseline, add base → crypto, crypto → policy and policy → directory. They reverse existing paths and create a cycle. The identity group is recalculated; the gateway and worker groups retain their local tables. A fresh recomputation rebuilds all three. In one measured run the incremental analysis took 0.35 ms and the full rebuild 1.16 ms. Counts of groups reused and equality of both schedules are repeatable; timings vary by machine and run.

Disconnected graph with a cycleThe disruption leaves the other two groups usable and returns benefit 71. In a two-node cyclic test, both patches are blocked, benefit 0; deleting the edges restores benefit 3.
Demand above available timeWith capacities [2,3] and jobs (2,6), (3,8), (3,7), (6,99), the reconstructed selection is a in window 1 and b in window 2. Benefit 14; c and heavy are deferred.
Item too large for each windowThe 25-minute queue action earns 40 but fits neither 18 nor 13. It is excluded even though pooled capacity is 31.

  Visit each dependency. Propagate child low links after return.
  For an edge to the active stack, use the neighbor’s discovery index.

DISCUSSION

Conclusion and limitations

The two decisions require different evidence. A capacity-feasible set with optimum benefit can still be unusable if the wrong patch runs first. A legal execution order can also leave valuable work out. Reconstructing the assignment and printing the order makes both decisions inspectable. The bounded multi-window solver proves optimal benefit within its model. Its greedy scheduler promises a legal ordering and uses urgency to choose between ready jobs.

Scope of the result

The dashboard’s Maintenance study tab accepts a reproducible synthetic case or a saved analysis snapshot and two editable capacities. The CLI accepts other approved-action datasets. Existing inventory, history and single-window comparison workflows continue separately. The new experiment is not saved as a database plan. The incremental cache is reused across the baseline and disruption within one experiment; it is not a persistent cross-user cache.

For one large, tightly connected group, local enumeration approaches exhaustive search. There are explicit limits on instance size, assignments per group and merge pairs. Exceeding a limit is a resource-limit condition, not evidence of infeasibility. Input estimates are fixed. There is no probabilistic patch failure, time-varying benefit, rollback duration, economic loss model or automatic deployment. A dependency graph models a partial order; an MST would discard required precedence edges, so a spanning-tree objective would be inappropriate here.
